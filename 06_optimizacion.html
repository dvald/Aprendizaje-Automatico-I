Escalabilidad: por qué Big O importa

La notación Big O describe cómo crece el número de operaciones de un algoritmo cuando aumenta el tamaño de la entrada n. Con pocos datos casi todos los algoritmos parecen igual de rápidos; el problema aparece cuando los datos crecen. Mueve el slider y observa cómo unas curvas se mantienen planas y otras se disparan.

Lo importante no es cuánto tarda un algoritmo hoy, con los datos de prueba, sino cómo crece al aumentar los datos. Un algoritmo O(n²) puede ir bien con 100 elementos y volverse inutilizable con 100.000. O(2ⁿ) y O(n!) son inviables salvo para entradas diminutas.

Buscar en list vs buscar en set

Elegir bien la estructura de datos suele importar mucho más que micro-optimizar líneas sueltas. Una lista guarda los elementos en orden y para saber si un valor está dentro debe recorrerlos uno a uno: búsqueda secuencial O(n). Un conjunto (set) usa una tabla hash: calcula directamente dónde debería estar el elemento, así que el acceso es O(1) en promedio.

Si vas a comprobar muchas veces si un elemento pertenece a una colección, usa un set (o las claves de un dict), no una lista. La diferencia no es de un 10 %: con un millón de elementos el set puede ser cientos de miles de veces más rápido. La estructura de datos correcta vale más que mil micro-optimizaciones.

Profiling: medir antes de tocar

Optimizar sin medir es perder el tiempo. Nuestra intuición sobre qué parte del código es lenta suele estar equivocada. El profiling mide el tiempo real consumido por cada parte del programa y nos dice exactamente dónde está el cuello de botella.

Función a analizar

def proceso(datos): limpiar(datos) transformar(datos) buscar_duplicados(datos) generar_resultado(datos)

Cuatro bloques. A simple vista, transformar parece el más "pesado"… pero no podemos saberlo sin medir.

Consumo de tiempo por bloque

Requieren extensiones instaladas (line_profiler, memory_profiler):

Se optimiza el código que realmente consume tiempo, no el que "parece feo" o el que más nos cuesta leer. Aquí el bloque lento es buscar_duplicados (68 %), aunque a primera vista nadie lo habría señalado.

Funciones integradas: menos código, mejor rendimiento

Python incluye funciones integradas (built-ins) para las operaciones más comunes: sum, max, min, all, any, map, sorted… Están implementadas internamente en C, así que son más rápidas que un bucle for equivalente escrito en Python, y además dejan el código más corto y legible.

Las cifras de velocidad son orientativas: el factor real depende del entorno (versión de Python, hardware) y del tamaño de los datos. Lo que no cambia es la tendencia: la built-in suele ganar.

Caso concreto: pasar una lista de palabras a mayúsculas

Tres formas de hacer lo mismo. La built-in y la list comprehension ganan.

FormaCódigoVelocidad relativaLegibilidad
Bucle for for p in palabras: r.append(p.upper()) 1,0× (referencia) Media
map() list(map(str.upper, palabras)) ≈ 1,6× más rápida Alta
List comprehension [p.upper() for p in palabras] ≈ 1,5× más rápida Muy alta

Velocidades relativas orientativas, medidas sobre listas grandes; varían según el entorno y el tamaño de los datos.

Las funciones integradas están implementadas en C; por eso son rápidas. Antes de escribir un bucle, pregúntate si ya existe una built-in que haga ese trabajo: el resultado será más corto, más legible y casi siempre más eficiente.

List comprehensions: transformar y filtrar

Una list comprehension combina en una sola línea tres pasos: recorrer una secuencia, filtrar con una condición y transformar cada elemento. Es más conciso que un bucle for con append y suele ser algo más rápido. Aquí lo vemos descompuesto pieza a pieza.

La misma sintaxis: set, dict y generadores

Los corchetes [ ] crean una lista. Cambiando el delimitador, la misma idea —recorrer, filtrar, transformar— construye otras estructuras.

Set comprehension

# conjunto: sin duplicados {x % 10 for x in numeros}

Con llaves { } se obtiene un set: elimina los valores repetidos automáticamente.

Dict comprehension

# diccionario clave: valor {k: k ** 2 for k in numeros}

Con llaves y pares clave: valor se construye un dict.

Expresión generadora — optimización de memoria

# paréntesis: NO construye la lista en memoria total = sum(i ** 2 for i in range(1_000_000))

Con paréntesis ( ) se obtiene un generador: produce los valores de uno en uno, sin almacenarlos todos. Una list comprehension crearía en memoria un millón de elementos; el generador apenas ocupa espacio. Es el compromiso tiempo–espacio aplicado: si solo vas a recorrer los valores una vez, usa un generador.

La list comprehension no es solo "código más corto": al escribirla, el patrón recorrer + filtrar + transformar queda explícito y se lee de un vistazo. Es la forma idiomática en Python de construir listas derivadas de otra secuencia.

Optimización real: de O(n²) a una solución razonada

Una demostración completa del proceso: partimos de una solución ingenua, la medimos, identificamos el problema y la mejoramos con razonamiento matemático.

El problema: contar cuántos productos i * j de dos números de cuatro cifras (de 1000 a 9999) son múltiplos de 11.

Versión ingenua: doble bucle anidado

contador = 0 for i in range(1000, 10000): for j in range(1000, 10000): if (i * j) % 11 == 0: contador += 1

Espacio de búsqueda: 9000 × 9000 combinaciones

Cada celda de esta cuadrícula representa un par (i, j). El grid completo tiene 81.000.000 de celdas; aquí se dibuja una versión simplificada.

Pulsa un botón para ver el resultado: cada paso de la optimización aparecerá aquí en paneles con sus cifras.

El patrón matemático

i * j es múltiplo de 11 si y solo si i es múltiplo de 11 O j es múltiplo de 11 (porque 11 es primo). Entonces no hace falta recorrer los 81 millones de pares: basta contar y aplicar combinatoria.
# Números de 4 cifras: 1000 … 9999 → 9000 valores # Múltiplos de 11 de 4 cifras: 1001 … 9999 → 819 valores mult = 819 no_mult = 9000 - 819 # = 8181 # Inclusión-exclusión: pares válidos = total - (ningún factor mult. de 11) validos = 9000**2 - no_mult**2 # = 81.000.000 - 8181**2 = 81.000.000 - 66.928.761 = 14.071.239

Big O nos avisa de que un doble bucle es O(n²); el profiling confirmaría dónde se va el tiempo; entender la estructura del problema (la propiedad de los números primos) permite sustituir 81 millones de operaciones por una fórmula. La mejor optimización casi nunca es escribir el mismo algoritmo más rápido: es cambiar de algoritmo.
